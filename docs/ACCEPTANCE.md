# 真實帳號驗收

日期：2026-10-15，台灣時間。版本：Local Memory Bridge 0.2.0。

## 結論

使用者在專用 Chrome 親自登入後，真實 DeepSeek 網頁橋接、兩回合記憶更新與專案檔案代理均通過。這是當次實帳結果，不代表永久免費、無限額度、服務穩定性或條款授權。

## 記憶與 HTTP API

以本機 HTTP API 完整經過「重新讀記憶 → 組包 → 核心 → 真實網頁服務 → 回答取回 → 本機紀錄」：

| 回合 | 驗收 | HTTP | 總時間 | 結果 |
|---|---|---|---|---|
| A | 只從 memory.md 讀取隨機暗號 | 200 | 9.384 秒 | 逐字相符 |
| B | 修改 memory.md，再讀取新暗號 | 200 | 8.655 秒 | 逐字相符 |

兩筆完成紀錄的 contextHash 不同，確認送出內容有更新。暗號未直接出現在使用者問題中。公開 model ID 為 `deepseek-v4-flash`，是橋接核心提供的別名，不能單憑此欄位證明上游實際模型版本。

## 真實檔案代理

在獨立測試專案執行一個任務，要求模型：讀取 source.txt 中的暗號、將它原樣寫到新 result.txt、再把 source.txt 的唯一「狀態：未完成」改為「狀態：已完成」。沒有在任務中提供檔案內的暗號。

實際工具順序：`read_file → create_file → replace_text → final`，共 4 次模型呼叫，總時間 25.893 秒。

主代理直接重新讀取本機檔案驗證：

- result.txt 的內容與來源暗號逐字相符，沒有額外換行。
- source.txt 只有指定狀態文字改變，其他內容一致。
- actions.jsonl 有 3 筆工具紀錄。
- 修改前備份有 1 份，對應原始來源檔內容。

驗收使用虛構資料，沒有修改使用者其他專案。登入態與私密 runtime 不包含在分享用 ZIP。

可自行查看 `examples/verified-run/` 中的原文、修改後實檔、新建檔、audit 與測試結果 JSON；全部是當次虛構測試資料，不含登入資訊。

## 實測發現與修正

1. 首次 Chrome 導頁及登入跳轉會造成程序中止：加上限定條件的 navigation race 處理與 6 項回歸測試。
2. 思考模式切換到回答時，某個 SSE 片段省略 operation，舊 parser 會漏掉 `CEPT`：從原始測試串流確認後修正 path/operation 繼承，新增 4 項回歸測試。修正版已通過上述真實兩回合。
3. 預設 8787 與這台電腦既有 Headroom 衝突：啟動腳本改用 18787，不停止或修改 Headroom。

## 功能界線

目前是 UTF-8 文字檔的受限專案代理：列出、讀取、新建、唯一文字替換。不是完整 coding agent；不執行 shell、安裝套件、啟動任意程式或刪除檔案。單檔 64 KiB，上下文 32,000 字元。修改與備份受檔案權限、磁碟狀態及同機外部程序影響，不能當作作業系統 sandbox。

此測試不能證明網頁服務符合所有自動化使用條款；條款風險見 PLAN.md。速度僅為這幾次短測試的觀察，不是效能保證。
